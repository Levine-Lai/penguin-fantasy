# 个人开发流程

你负责提出需求、看效果和决定取舍；开发助手负责检查代码、实现、验证和说明。普通改字和样式无需反复审批，存在会改变结果的歧义时才集中询问。

1. **定结果**：先用 3–5 条描述完成后能看到什么。举例：“每行四边框；六行内滚动；320px 下章节名和分数框不重叠；红绿白含义保留”。助手给出一句理解和影响范围，然后开始。
2. **做小改动**：检查工作区，从最新 `origin/main` 创建 `codex/任务名`。已有未提交内容先保存并说明位置。一个分支处理一项完整需求，不把样式、比赛规则和数据库调整混在一次顺手整理中。
3. **验收**：运行 `npm run verify`，它依次执行 lint、构建后测试、静态构建、浏览器验收。首次先 `npm ci`、`npx playwright install chromium`。本地根路径验收前在 PowerShell 设置 `$env:NEXT_PUBLIC_BASE_PATH=""`。涉及规则还需检查相等、零分、未出场、未结算和重复执行等实际相关边界。
4. **审阅与合并**：开 PR（一次修改的对照记录），写目的、验收、验证和恢复方式。GitHub 的 `Verify project` 检查通过再合并；单人项目不强求第二人批准。不为凑流程重写完整方案。发布前的代码审阅只报告问题，不自动修正无关内容。
5. **双站发布与回报**：GitHub Pages 自动部署 main；成功后在干净的同一 main 提交上运行 `npm run release`（本机 PowerShell 与 Wrangler 登录）。它核对提交与 GitHub 部署、构建根路径版本、发布 Cloudflare，再自动运行 `npm run verify:online`。两边 `release.json` 的提交 SHA 和快照哈希必须一致。最后告诉你改了什么、验证结果、链接与已知限制。Worker 变更仍按 AGENTS.md 独立验证发布。

## 减少修复成本

- 新界面先查已有同类组件，沿用品牌颜色变量、四档主要字号、冰框素材和布局。新需求只描述与现有样式不同的部分，助手负责找对应参照。
- 同一组件的布局只有一个维护位置。新增布局用 CSS Module；修改原规则，避免继续在全局 CSS 尾部加覆盖。历史记录现由 `app/components/captain-history.tsx` 和同目录样式负责，决斗由 `app/arena/live-arena.*` 负责。
- 文字列用 `minmax(0, 1fr)`，长文本允许换行；分数和血量保留独立空间，内容容器不设会裁字的固定高度。允许省略名称时要保留完整名称可访问方式。不要靠缩小到不可读来通过验收。
- 共享代码在出现实际重复时提取。此次只拆出反复调整的历史记录组件；其余旧全局样式随相关需求逐步清理，不一次重写全站。
- 计分规则集中在现有规则函数，展示只读取结果。界面刷新和正式结算分开，防止“看到了新分数”就提前扣血。

## 数据与构建

构建使用提交中的 `app/static-fpl-data.json`，不在构建前静默拉取线上数据。需要更新降级快照时明确运行 `npm run sync:fpl-snapshot`，检查名单和差异后一起提交。两个站点因此能从同一提交构建出同一数据版本。移除原每日单站重建；网页仍按既有逻辑从公共 API 获取每日数据，Worker 每日 07:30 发布流程不变。
